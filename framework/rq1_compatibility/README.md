# RQ1 Compatibility Analysis

This directory contains the RQ1-only compatibility judgment and metric workflow. Shared benchmark data and semantic-description generation remain in [`../../benchmark/`](../../benchmark/); this directory contains only the RQ1 negative input, judgment contract, offline preparation, response parsing, and metric calculation.

## Logic Chain

```text
benchmark/benchmark_data.json (positive source)
        +
inputs/neg_406.json (negative source)
        |
        v
prepare_inputs.py
        |  validates IDs and builds runtime semantic-generation inputs
        v
Generate semantic_description with benchmark/prompts/semantic_description_generation.txt
        |  keep it in a runtime artifact; do not edit either base file
        v
prompts/compatibility_judgment.txt
        |  model receives semantic_description only
        v
user-provided model response JSONL
        |
        v
parse_predictions.py
        |  valid binary prediction or non-binary/invalid/unparsed status
        v
calculate_metrics.py
        |
        v
Accuracy, Precision, Recall, F1, confusion matrix, and status counts
```

There is deliberately no published positive/negative merged JSON. The preparation output is a disposable runtime manifest generated from the two source files.

## Preconditions

1. Python 3.10 or newer is available. The scripts use only the Python standard library.
2. `benchmark/benchmark_data.json` exists, parses as a JSON array, has unique `row_id` values, and contains no `semantic_description` key.
3. `inputs/neg_406.json` exists, parses as a JSON array, contains the RQ1 negative records, and contains no `semantic_description` key.
4. Every selected case supplies test-case code. Registration metadata is not supplied to semantic-description generation.
5. Before compatibility judgment, every runtime case must have a non-empty `semantic_description` generated by the shared benchmark prompt. A missing or empty value is a failed precondition, not an invitation to use names or raw code as a substitute.
6. The user configures the large-model API invocation, including the endpoint, credentials, client or runner, and writes raw responses to JSONL. Credentials remain user-managed and are not stored in this repository.

## Input and Label Contract

The positive label is `compatible`: each benchmark record has a selected Vulkan counterpart. The negative label is `incompatible`: records read from `neg_406.json` are assigned this fixed label from their source-dataset role, not from an in-record label field. Labels are preserved in the runtime manifest and are never inferred from a model response.

The source schemas remain separate. `prepare_inputs.py` adapts them at runtime and assigns a stable `record_id`: `row_id` for positive records and the unique source `qualified_name` for negative records. It does not rewrite either source or create a canonical merged benchmark file.

## Run Order

Run every public command from the repository root. Choose a user-owned `<run-root>` outside the published source tree, or an ignored local run directory, before starting. Every semantic description, model response, prediction, metric file, and model/run record belongs under that runtime root and must not be committed.

### Step 1: Prepare the runtime requests

**Prerequisites:**

- Python 3.10 or newer is available, and the command is run from the repository root.
- `benchmark/benchmark_data.json` and `framework/rq1_compatibility/inputs/neg_406.json` exist, are readable JSON arrays, and contain no `semantic_description` field.
- Every source record has a stable ID and non-empty test-case code; the combined positive and negative IDs are unique.
- `<run-root>/rq1/` is writable and is outside the published source tree or ignored by Git.

```text
python framework/rq1_compatibility/scripts/prepare_inputs.py --output <run-root>/rq1/requests.jsonl
```

This command reads all 406 positive benchmark records and all 406 negative records by default. Each output line contains a stable `record_id`, its fixed label, and the two `semantic_generation_inputs` required by the shared prompt:

```json
{
  "record_id": "44",
  "label": "compatible",
  "semantic_description": null,
  "semantic_generation_inputs": {
    "test_case_code": "...",
    "base_class_code": "..."
  }
}
```

`semantic_description` is intentionally `null` at this point. Do not edit either public source dataset to fill it.

**Completion check:** The command exits successfully; the default inputs produce 812 JSONL records; every `record_id` is unique; every label is the fixed source label; every record contains exactly `test_case_code` and `base_class_code` under `semantic_generation_inputs`; and every `semantic_description` is `null`.

### Step 2: Apply the shared semantic-description prompt

**Prerequisites:**

- Step 1 completed, and `requests.jsonl` is readable with one unique `record_id` per request.
- [`../../benchmark/prompts/semantic_description_generation.txt`](../../benchmark/prompts/semantic_description_generation.txt) is readable and is used without changing its instructions.
- Each request has non-empty `test_case_code`. `base_class_code` may be empty only when the source genuinely provides no inheritance context.
- A model-call mechanism is available. Its exact model identity and experiment settings are recorded outside the repository, and the runtime output directory is writable.

For every line in `requests.jsonl`:

1. Read [`../../benchmark/prompts/semantic_description_generation.txt`](../../benchmark/prompts/semantic_description_generation.txt).
2. Replace `{{TEST_CASE_CODE}}` with `semantic_generation_inputs.test_case_code`.
3. Replace `{{BASE_CLASS_CODE}}` with `semantic_generation_inputs.base_class_code`.
4. Confirm that no template placeholder remains.
5. Send the rendered prompt through the model-call mechanism used by your experiment.
6. Require one valid JSON object containing one non-empty string:

```json
{
  "semantic_description": "One concise API-independent description of the tested functionality."
}
```

Store the derived value in a user-owned runtime file such as `<run-root>/rq1/runtime_semantics.jsonl`, preserving the source `record_id`:

```json
{
  "record_id": "44",
  "semantic_description": "One concise API-independent description of the tested functionality."
}
```

Stop and record a failed precondition if the model response is missing, malformed, empty, or contains an unresolved placeholder. Do not substitute a test name or raw code for a missing semantic description.

**Completion check:** There is exactly one valid, non-empty `semantic_description` for every request `record_id`; the output ID set and record count match `requests.jsonl`; and no rendered prompt contains an unresolved placeholder. If any call fails, keep the failure record, do not invent replacement data, and treat Step 2 as incomplete.

### Step 3: Apply the compatibility-judgment prompt

**Prerequisites:**

- Step 2 produced exactly one validated semantic description for every request `record_id`, with no missing or duplicate IDs.
- [`prompts/compatibility_judgment.txt`](prompts/compatibility_judgment.txt) is readable and is used without changing its instructions.
- The model-call mechanism and recorded experiment settings are available, and `<run-root>/rq1/` is writable.

For every prepared request and its validated semantic description:

1. Read [`prompts/compatibility_judgment.txt`](prompts/compatibility_judgment.txt).
2. Replace `{{SEMANTIC_DESCRIPTION}}` with the generated `semantic_description`.
3. Confirm that the placeholder no longer remains.
4. Send the rendered prompt through the model-call mechanism used by your experiment.
5. Preserve the raw model text together with the same `record_id`.

Configure the large-model API invocation in the user's environment, either through a client, script, or runner. Preserve the published prompt text and JSON contracts, and record the exact model identity and experiment settings in user-owned run metadata. Never place credentials in the repository.

Write one result per line to `<run-root>/rq1/responses.jsonl` with at least:

```json
{
  "record_id": "44",
  "raw_response": "{\"compatibility\":\"compatible\",\"reason\":\"...\"}"
}
```

The inner `raw_response` must be the model's unmodified answer to `compatibility_judgment.txt`. Keep exactly one current response for each `record_id`; missing responses are reported explicitly by the parser.

**Completion check:** `responses.jsonl` contains exactly one raw response for every request `record_id`; its ID set and record count match `requests.jsonl`; and each model answer follows the published `compatibility` and `reason` JSON contract. If any answer is missing or malformed, preserve that outcome for reporting, do not repair, relabel, or fabricate it, and treat Step 3 as incomplete.

### Step 4: Parse the model responses

**Prerequisites:**

- Step 1's `requests.jsonl` and Step 3's `responses.jsonl` are readable UTF-8 JSONL files.
- Manifest and response `record_id` values are unique, response IDs refer to manifest records, and the fixed source labels have not been edited.
- The output directory is writable.

```text
python framework/rq1_compatibility/scripts/parse_predictions.py --manifest <run-root>/rq1/requests.jsonl --responses <run-root>/rq1/responses.jsonl --output <run-root>/rq1/predictions.jsonl
```

The parser joins the files by `record_id` and records a valid binary prediction or a non-binary, invalid, unparsed, or missing-response status without guessing a binary label.

**Completion check:** The command exits successfully; `predictions.jsonl` has one row for every manifest request; every row preserves its `record_id` and fixed label and has an explicit status; and missing, non-binary, or malformed responses have not been silently converted to a binary prediction.

### Step 5: Calculate the RQ1 metrics

**Prerequisites:**

- Step 4 completed, and `predictions.jsonl` is a readable JSONL file produced from the complete manifest.
- No non-binary, invalid, unparsed, or missing-response row has been deleted before calculation.
- The metrics output directory is writable.

```text
python framework/rq1_compatibility/scripts/calculate_metrics.py --predictions <run-root>/rq1/predictions.jsonl --output <run-root>/rq1/metrics.json
```

`parse_predictions.py` never silently maps non-binary responses, malformed JSON, or missing responses to the negative class. `calculate_metrics.py` reports those statuses separately and computes classification metrics only over explicitly labeled records with valid binary predictions.

**Completion check:** The command exits successfully and creates `metrics.json`; `total_records` equals the number of prediction rows; all `status_counts` sum to `total_records`; the four confusion-matrix cells sum to `valid_labeled_records`; and Accuracy, Precision, Recall, and F1 are present.

## Runtime Artifact Map

| Artifact | Producer | Consumer or purpose |
| --- | --- | --- |
| `requests.jsonl` | `prepare_inputs.py` | Stable IDs, labels, and semantic-generation inputs |
| `runtime_semantics.jsonl` | User model-call step | Auditable mapping from each `record_id` to its generated semantic description |
| `responses.jsonl` | User model-call step | Raw compatibility answers consumed by `parse_predictions.py` |
| `predictions.jsonl` | `parse_predictions.py` | Normalized prediction, status, reason, and fixed label |
| `metrics.json` | `calculate_metrics.py` | Confusion matrix, metrics, and explicit status counts |

`runtime_semantics.jsonl` is a recommended user-owned audit artifact; the filename is not hard-coded by the public scripts. The files under `<run-root>` are derived runtime products, not additions to the public benchmark.

## Metric Semantics

`compatible` is the positive class. The confusion matrix is:

```text
                 predicted compatible   predicted incompatible
actual compatible       TP                       FN
actual incompatible     FP                       TN
```

Accuracy, Precision, Recall, and F1 use the standard binary definitions. Zero-denominator values are `0.0`. The report also includes total records, valid labeled records, invalid/unparsed records, non-binary records, and missing responses.

## Scope Boundary

This workflow measures compatibility judgment only. It does not measure RQ2 retrieval quality, migration-generation success, compilation success, runtime execution, or repair success.
